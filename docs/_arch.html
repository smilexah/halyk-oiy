Maqsat & Family — Архитектура

Микросервисный бэкенд для Halyk SuperApp: AI-бюджетирование · цели/накопления · семейный контур с детскими лимитами и SOS-одобрением.  •  2026

1. Что это

  • AI-бюджетирование — доход разбивается на категории; траты авто-категоризируются по MCC и трекаются против бюджета.
  • Цели / Maqsat — накопления на виртуальных счетах с прогрессом.
  • Family — общие группы, роли adult/child, дневные лимиты. Ключевой сценарий: ребёнок упёрся в лимит на кассе → SOS-push родителю → одобрение в один тап.

Стек: Java 21 · Gradle (Kotlin DSL) monorepo · Spring Boot 3.4.1 · Spring Cloud 2024.0.0 · Gateway (reactive) · Eureka · PostgreSQL 16 (db-per-service, Flyway) · Kafka 3.9 (KRaft) · Keycloak 26 (OIDC) · Micrometer/OTel → Prometheus/Tempo/Loki/Grafana.

2. Принципы

  • Виртуальный слой — деньги на основном счёте; лимиты накладываются маской через API, процессинг банка не трогаем.
  • Инвайты без передачи пароля — приглашённому создаётся временный пароль с обязательной сменой (UPDATE_PASSWORD).
  • Роли в домене — adult/child в family-service (привязаны к membership), не в Keycloak. Keycloak отвечает только «кто ты» (sub).
  • Тонкий common — только контракты событий, ApiError, CurrentUser.
  • Состояние через Kafka; синхронные чтения — REST/WebClient через Eureka (lb://).

6. Конфликтный сценарий (ядро продукта)

  1. Ребёнок: POST /api/transactions на 5000 при лимите 3000.
  2. transaction читает лимит из family (lb WebClient, проброс bearer ребёнка).
  3. Превышение → транзакция в статус PENDING_APPROVAL (не отклоняется) + publish LimitExceeded.
  4. notification консьюмит → SOS Smart-Push родителю «одобрить транзакцию?».
  5. Родитель: POST /api/family/approvals/{txnId} → family пишет override в child_limit + publish LimitOverrideApproved.
  6. transaction консьюмит → проводит платёж (POSTED) + publish TransactionCategorized (учёт в бюджете).

7. Модель данных (database-per-service, Flyway, id uuid pk)

budget_db

  • budget_plan(owner_id, owner_type[USER|GROUP], period_start, period_end, created_at)
  • budget_category(plan_id→plan, name, type[MANDATORY|DISCRETIONARY], limit_amount, spent_amount)

transaction_db

  • txn(account_id, user_id, amount, merchant, mcc, category_name, occurred_at, status[POSTED|DECLINED|PENDING_APPROVAL])

goals_db

  • virtual_account(owner_id, owner_type, balance)
  • goal(name, target_amount, allocated_amount, monthly_contribution, deadline, virtual_account_id→va, bonus_program_ref)

family_db

  • family_group(name, type='FAMILY', created_by, created_at)
  • membership(group_id→group, user_id, role[ADULT|CHILD], unique(group_id,user_id))
  • child_limit(membership_id→membership, daily_limit, override_until, override_amount)

10. Безопасность

  • Keycloak realm maqsat: клиент maqsat-app (public, password grant), maqsat-admin (confidential, service-account с realm-management ролями), realm-роль CUSTOMER, юзеры papa/mama/child.
  • Каждый сервис — OAuth2 resource server: валидация JWT по issuer-uri, STATELESS, permitAll для actuator/swagger.
  • sub = кросс-сервисный userId (через CurrentUser). KC_HOSTNAME фиксирует iss, чтобы хостовые и in-network токены валидировались одинаково.
  • Сервис→сервис: проброс Bearer инициатора.

11. Observability

  • Метрики — Micrometer → Prometheus (Eureka SD) + кастомные бизнес-счётчики (транзакции по статусу, лимиты, одобрения, трекинг трат).
  • Трейсы — OTLP → Tempo; один трейс проходит gateway→transaction→Kafka→budget/notification/integration (контекст через Kafka-заголовки). Tempo строит service graph.
  • Логи — ECS JSON (traceId/spanId), Alloy → Loki. Двусторонняя корреляция trace↔log в Grafana.
  • 3 дашборда: Overview, Service Graph & Traces, Business Metrics.
